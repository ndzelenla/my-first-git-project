## Broken Config 1: The DAG That Never Stops Changing
# Diagnosis
What is wrong:

start_date=datetime.now() changes every time the DAG file is parsed

Airflow's scheduler parses DAG files every ~30 seconds

Each parse creates a NEW start_date, so Airflow thinks the DAG definition keeps changing

The DAG may never trigger because start_date keeps moving into the future

Why it matters:

start_date must be STATIC — it defines when the first data interval begins

A moving start_date makes scheduling unpredictable and breaks catchup logic

Airflow may create unexpected DAG runs or none at all

The Fix
python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

with DAG(
    dag_id="daily_sales_report",
    start_date=datetime(2024, 1, 1),    # Fixed: static date in the past
    schedule_interval="@daily",
    catchup=False,
) as dag:
    generate_report = PythonOperator(
        task_id="generate_report",
        python_callable=generate_sales_report,
    )

## Why this works:

datetime(2024, 1, 1) is a fixed, immutable value

Every DAG file parse sees the exact same start_date

Airflow can consistently determine when the next schedule should trigger

The scheduler behaves predictably



## Broken Config 2: The DAG That Spawns 180 Runs
# Diagnosis
What is wrong:

start_date is 6 months in the past (2024-01-01)

catchup=True tells Airflow to create a DAG run for EVERY missed interval

With @daily schedule, that means ~180 DAG runs are created immediately

The scheduler will try to execute all 180 runs, overwhelming resources

Why it matters:

Catchup is useful for backfilling historical data, but it must be intentional

Unintended backfills can overload the scheduler, database, and workers

Each run consumes resources and may hit API rate limits or database connections

Can bring down your entire Airflow infrastructure

The Fix
python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

with DAG(
    dag_id="customer_sync",
    start_date=datetime(2024, 1, 1),
    schedule_interval="@daily",
    catchup=False,                       # Fixed: only run the latest interval
) as dag:
    sync_customers = PythonOperator(
        task_id="sync_customers",
        python_callable=sync_customer_data,
    )
Alternative fix (if backfill IS intended):

python
with DAG(
    dag_id="customer_sync",
    start_date=datetime(2024, 1, 1),
    schedule_interval="@daily",
    catchup=True,
    max_active_runs=3,                    # Limits concurrent backfill runs
) as dag:
    sync_customers = PythonOperator(
        task_id="sync_customers",
        python_callable=sync_customer_data,
    )
Why these work:

catchup=False tells Airflow to only schedule the latest interval, ignoring historical gaps

max_active_runs=3 (if backfill needed) prevents resource exhaustion by limiting concurrency

For controlled historical loads, use the airflow dags backfill CLI command



## Broken Config 3: The Non-Deterministic Task
# Diagnosis
What is wrong:

The task uses datetime.now() to determine which date's data to process

This is NON-DETERMINISTIC: if you re-run the task tomorrow, it processes different data

If the DAG runs at 11:58 PM, datetime.now() gives today's date

If the DAG runs at 12:02 AM (delayed), datetime.now() gives tomorrow's date

Backfills are broken: re-running the Jan 15 DAG on Feb 1 processes Feb 1 data

Why it matters:

Airflow tasks must be IDEMPOTENT and DETERMINISTIC

The date should come from execution_date, not wall-clock time

Re-running any DAG should produce the same result regardless of when it runs

Data pipelines need consistent, repeatable results for auditing and debugging

The Fix
python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

def process_daily_data(**context):
    """Process data for the execution date's data interval."""
    target_date = context["ds"]                          # Fixed: uses execution_date
    query = f"SELECT * FROM orders WHERE order_date = '{target_date}'"
    print(f"Processing data for: {target_date}")
    # ... execute query ...

with DAG(
    dag_id="daily_order_processing",
    start_date=datetime(2024, 1, 1),
    schedule_interval="@daily",
    catchup=False,
) as dag:
    process = PythonOperator(
        task_id="process_daily_data",
        python_callable=process_daily_data,
        provide_context=True,                            # Enables **context
    )
Why this works:

context["ds"] provides the execution_date in YYYY-MM-DD format (e.g., "2024-01-15")

The date is determined by Airflow's schedule, not wall-clock time

Re-running the DAG for any historical date will always process the correct data

The task becomes idempotent and deterministic



## Broken Config 4: The DAG That Never Triggers
# Diagnosis
What is wrong:

start_date is set to 2099-01-01 — far in the future

Airflow triggers a DAG run at the END of its first data interval

First data interval: 2099-01-01 to 2099-01-02 → first run triggers 2099-01-02

The DAG will NEVER trigger because the first interval hasn't ended yet

The DAG appears in the Airflow UI but shows no runs

Why it matters:

start_date must be in the PAST (or at most, today) for the DAG to trigger

A common mistake when copying DAG templates or placeholder dates

This can make you think your DAG is broken when it's just waiting for 2099

Wastes debugging time on a simple configuration error

The Fix
python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

with DAG(
    dag_id="new_feature_pipeline",
    start_date=datetime(2024, 6, 1),     # Fixed: a date in the past
    schedule_interval="@daily",
    catchup=False,
) as dag:
    run_pipeline = PythonOperator(
        task_id="run_pipeline",
        python_callable=run_feature_pipeline,
    )
Why this works:

With start_date in the past (e.g., 2024-06-01), the first data interval has already ended

Airflow immediately schedules the first run (or catches up if catchup=True)

The DAG triggers as expected on the schedule

For testing, you can use datetime.now() - timedelta(days=1) to ensure it's always in the past


## Broken Config 5: The Template-Unaware Midnight Task
# Diagnosis
What is wrong:

The task computes "yesterday" using datetime.today() - timedelta(days=1)

This is wall-clock time — NOT the Airflow execution_date

The schedule "0 0 * * *" means the DAG runs at midnight to process the previous day's data

Airflow already handles this: execution_date IS the previous day (the data interval start)

Problem 1: If the task retries at 1 AM the next day, "yesterday" now points to the wrong date

Problem 2: Manual backfills process the wrong date

Problem 3: Result depends on wall-clock time, breaking idempotency

Why it matters:

{{ ds }} already gives you the data interval start date (which IS "yesterday" for @daily)

Using Airflow templates ensures deterministic, repeatable behavior

Data partitions based on execution_date ensure proper backfill and retry behavior

Prevents silent data corruption from processing wrong dates

The Fix
python
from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.operators.bash import BashOperator
from datetime import datetime

def process_yesterdays_data(**context):
    """Process data for the execution date's interval using Airflow templates."""
    target_date = context["ds"]                           # Fixed: deterministic date
    file_path = f"/data/raw/{target_date}/events.csv"     # Uses execution_date
    print(f"Processing file: {file_path}")
    # ... read and process file ...

with DAG(
    dag_id="daily_event_processing",
    start_date=datetime(2024, 1, 1),
    schedule_interval="0 0 * * *",
    catchup=False,
) as dag:
    process = PythonOperator(
        task_id="process_yesterdays_data",
        python_callable=process_yesterdays_data,
        provide_context=True,
    )

################   Airflow Scheduling Cheat Sheet
## Scheduling Cheat Sheet

| Concept                | Wrong Way                          | Right Way                       |
|------------------------|------------------------------------|---------------------------------|
| start_date             | datetime.now()                     | datetime(2024, 1, 1)           |
| Target date in task    | datetime.today()                   | context["ds"] or {{ ds }}       |
| File date (no dashes)  | datetime.now().strftime('%Y%m%d')  | {{ ds_nodash }}                 |
| Yesterday's date       | datetime.today() - timedelta(1)    | {{ yesterday_ds }}              |
| Tomorrow's date        | datetime.today() + timedelta(1)    | {{ tomorrow_ds }}               |
| Data range start       | Manual calculation                 | {{ data_interval_start }}       |
| Data range end         | Manual calculation                 | {{ data_interval_end }}         |
| Avoid mass backfill    | catchup=True (default)             | catchup=False                   |
| Limit concurrent runs  | No limit (overwhelms system)       | max_active_runs=3               |
| Schedule definition    | "0 0 * * *" (cryptic)              | "@daily" (readable presets)     |
| Task idempotency       | Uses wall-clock time               | Uses execution_date templates   |

## Scheduling Rules
1. **start_date must be STATIC** (never datetime.now() or dynamic values)
2. **execution_date = start of data interval** (NOT when the task actually runs)
3. **First run triggers at END of first interval** (never at start_date)
4. **Tasks must be DETERMINISTIC** — use templates, not wall-clock time
5. **catchup=False unless you intentionally want backfills** (protect production)
6. **Data intervals are [start, end)** — includes start, excludes end
7. **{{ ds }} is your friend** — always use it for date-based partitioning
8. **Test with future dates** — set start_date in the past, not future

## Common Cron to Preset Mappings
| Preset     | Cron Expression | Meaning                          |
|------------|-----------------|----------------------------------|
| @once      | None            | Schedule once and only once      |
| @hourly    | 0 * * * *       | At the start of every hour       |
| @daily     | 0 0 * * *       | At midnight every day            |
| @weekly    | 0 0 * * 0       | At midnight every Sunday         |
| @monthly   | 0 0 1 * *       | At midnight first day of month   |
| @yearly    | 0 0 1 1 *       | At midnight on January 1st       |

## Template Variables Cheat Sheet
| Template          | Format Example        | Description                         |
|-------------------|----------------------|-------------------------------------|
| {{ ds }}          | 2024-01-15           | Execution date (YYYY-MM-DD)         |
| {{ ds_nodash }}   | 20240115             | Execution date without dashes       |
| {{ yesterday_ds }}| 2024-01-14           | Previous day (YYYY-MM-DD)           |
| {{ tomorrow_ds }} | 2024-01-16           | Next day (YYYY-MM-DD)               |
| {{ ts }}          | 2024-01-15T00:00:00  | Execution date with timestamp       |
| {{ ts_nodash }}   | 20240115T000000      | Timestamp without separators        |
