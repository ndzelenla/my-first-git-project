--- Select the primary key

Choose the best identifier for each Entity - customer Entity - Primary key : customer_id, 
Consider uniqueness, stability, and simplicity - Uniqueness Guaranteed: Auto-increment ensures no duplicates, Stability: Never changes (emails can change, causing foreign key issues), Simplicity: Single integer, easy to reference in foreign keys
Explain why it uniquely identifies records -email (Natural Key)- Volatility: Customers can change email addresses

-- For orders: Order Entity
- Selected Primary Key: order_id (Surrogate Key)
Why order_id?

Business Requirement: Orders need unique identifiers for tracking

Stability: Order IDs should never change once assigned

Simplicity: Single integer field, easy for customers to reference

-- For Products:
- Selected Primary Key: product_id (Surrogate Key)
Why product_id?

Stability: Internal ID never changes even if SKU changes

Performance: Integer joins faster than string-based SKU joins

Simplicity: Consistent with other entity keys

-- SKU as Natural Key - Why Not Primary?

Format Changes: SKU numbering schemes may evolve

Business Mergers: SKU formats might conflict during acquisitions

Length Issues: SKUs can be long strings (less efficient)

Order → Customer
- Relationship: One customer can have many orders
- Foreign key: Order.customer_id → Customer.customer_id
- Required: Yes (every order must have a customer)

OrderItem → Order
- Relationship: One order can have many order items
- Foreign key: OrderItem.order_id → Order.order_id
- Required: Yes (every order item must belong to an order)

OrderItem → Product
- Relationship: One product can appear in many order items
- Foreign key: OrderItem.product_id → Product.product_id
- Required: Yes (every order item must reference a product)

Composite Key Analysis (10 mins)
Why order_id + product_id is a composite key - In the OrderItem table, we need to track which products are in which orders. This is a classic many-to-many relationship

Explain why both columns are needed - Only One Product Per Order: Primary key constraint prevents adding multiple products to same order
What makes this combination unique - Uniqueness: Each product appears only once per order (quantity handles multiples)
Why a single column wouldn't work - Business Logic Violation: Orders typically contain multiple products
What breaks if only one column is used - Product Exclusivity: Each product can only appear in ONE order ever

What problems would occur with only order_id - Only One Product Per Order: Primary key constraint prevents adding multiple products to same order
What problems would occur with only product_id - Product Exclusivity: Each product can only appear in ONE order ever
Why the combination is necessary - The composite key (order_id, product_id) perfectly models the business rule:

Uniqueness: Each product appears only once per order (quantity handles multiples)
