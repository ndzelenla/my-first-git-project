###  Step 2: Group Pipelines into DAGs
DAG 1: Core_ETL (core_etl_dag)
Property	                  Value
Pipelines Included	       orders_etl, inventory_sync
Schedule	               orders_etl: 2:00 AM daily
                               inventory_sync: 0 */4 * * * (every 4 hours)
start_date	               2024-01-01
catchup	                       False

# Why These Are Grouped Together:

- Both are source-adjacent pipelines with no upstream dependencies

- They represent the "raw ingestion" layer of the architecture

- Grouping them reduces the number of DAGs while maintaining independent schedules (using multiple tasks with different schedules in one DAG is possible but not ideal — see Alternative Grouping below)


# Why Not Separate DAGs?

- They could be separate DAGs, and that's actually a better design given their completely different schedules

- Alternative: Split into two DAGs (orders_etl_dag and inventory_sync_dag) for cleaner separation

# Task Dependencies:

- No dependencies between tasks — they run independently

# Cross-DAG Dependencies:

- None (these are root DAGs)


DAG 2: Customer_360 (customer_360_dag)
Property	            Value

Schedule	            4:00 AM daily
start_date	            2024-01-01

# Why These Are Grouped Together:

- Direct sequential dependency: ml_feature_pipeline needs customer_360 output

- Same data domain (customer data)

# Why Not Separate DAGs?

Step 3: Define Cross-DAG Dependencies
Cross-DAG Dependency: core_etl_dag (orders_etl) → customer_360_dag
Property	Value
Mechanism	Dataset
Why this mechanism?	Dataset triggers are native to Airflow 2.4+, clean, and reduce sensor load on scheduler. customer_360 should trigger as soon as orders_etl data is ready.
What happens if upstream is late?	Sensor timeout: N/A (Dataset waits indefinitely) — but we set SLA alerts
Fallback action	Alert data team if orders_etl not complete by 3:30 AM
Upstream fails?	customer_360 waits; alert triggers; manual intervention may be needed
Alert	#data-pipeline-alerts (Slack)


Cross-DAG Dependency: core_etl_dag (inventory_sync) → product_data_dag
Property	Value
Mechanism	ExternalTaskSensor
Why this mechanism?	product_catalog needs the specific inventory_sync run from the same day. Dataset would trigger on any update, but we need yesterday's inventory.
Sensor timeout	6 hours (must complete by 9:00 AM)
Fallback action	If inventory_sync fails, product_catalog uses yesterday's data + alert
Upstream fails?	ExternalTaskSensor will fail after timeout; product_catalog task skipped
Alert	#product-team-alerts


Cross-DAG Dependency: customer_360_dag & product_data_dag → bi_dag (data_quality)
Property	Value
Mechanism	Datasets (multiple)
Why this mechanism?	data_quality_checks needs both customer AND product data to be fresh. Dataset on each, with AND logic.
What happens if upstream is late?	bi_dag waits for both datasets; SLA alert at 6:00 AM if not ready
Fallback action	Skip data_quality but still run reports? NO — quality must pass first
Upstream fails?	bi_dag never triggers; manual investigation required
Alert	PagerDuty (critical — executives need reports by 7 AM)




Step 4: Choose the Executor
ShopStream's Workload Profile
Metric	Value
Total pipelines	8 (4-5 DAGs with 8-10 tasks total)
Max concurrent tasks	3-5 (morning peak: daily reports + weekly analytics)
Peak resource need	weekly_analytics (45-60 min, heavy queries)
Team size	6 engineers
Current infra	Single VM (migrating to cloud)
Growth plan	Moderate growth (2-3 new pipelines per year)

Recommended Executor: CeleryExecutor

Justification
Parallelism needs: 3-5 concurrent tasks requires more than LocalExecutor's single-node capacity

Operational complexity: Team of 6 can manage Celery (Redis/RabbitMQ) with proper documentation

Scalability: Can add workers as ShopStream grows; supports 20-50 tasks easily

Cost: Moderate — can run on small VM cluster or cloud instances

Fault tolerance: Tasks can be retried on different workers if one fails



Why NOT the other executors?
Executor	Reason for Rejection
SequentialExecutor	Zero parallelism — pipelines would run one at a time, missing SLAs
LocalExecutor	Single machine bottleneck; weekly_analytics could starve other tasks
KubernetesExecutor	Overkill for current scale; adds significant complexity; team not Ready

Failure Scenarios Analysis
Scenario 1: orders_etl fails at 2:15 AM due to DB timeout
Impact:

customer_360 (DAG 2) waits — never triggers if using Dataset

ml_feature_pipeline also waits

data_quality_checks (DAG 4) waits for both customer_360 AND product_data

daily_reports (DAG 4) waits for data_quality

weekly_analytics eventually affected

Recovery:

Retry logic activates (3 retries with backoff)

If still failing by 3:00 AM, alert triggers

Data engineer investigates DB connectivity

Once fixed, manually clear orders_etl task and re-run

All downstream DAGs automatically trigger upon completion

Prevention: Consider read-replica for reporting to avoid production DB load



Scenario 2: inventory_sync API timeout (10% failure rate)
Strategy:

High retry count (5) with exponential backoff

Only alert on 3+ failures to avoid noise

If all 5 retries fail, mark task as failed but allow product_catalog to use cached data

Code:

python
inventory_sync = PythonOperator(
    task_id='inventory_sync',
    python_callable=sync_inventory,
    retries=5,
    retry_delay=timedelta(minutes=2),
    retry_exponential_backoff=True,
    max_retry_delay=timedelta(minutes=30),
    on_retry_callback=lambda ctx: logging.info(f"Retry {ctx['ti'].try_number} of 5"),
    dag=dag
)


Scenario 3: weekly_analytics takes 90 minutes instead of 60
Impact:

No other pipelines blocked (it's the last task in BI DAG)

But it consumes worker resources longer

Prevention:

Set task timeout to 90 minutes (kill if exceeded)

Use different Celery worker queue for heavy tasks

Optimize queries or break into parallel chunks

Scenario 4: data_quality_checks detects a problem
Policy:

NEVER run daily_reports if data_quality fails

Quality check must pass OR be explicitly overridden by data engineer

Override mechanism: Airflow Variable skip_quality_checks set to True (with audit log)

Implementation:

python
def check_quality_and_continue(**context):
    quality_passed = context['ti'].xcom_pull(task_ids='data_quality_checks')
    skip_flag = Variable.get('skip_quality_checks', default_var=False)
    
    if not quality_passed and not skip_flag:
        raise AirflowSkipException("Data quality failed - blocking reports")
    elif not quality_passed and skip_flag:
        logging.warning("Data quality failed but override enabled - PROCEED WITH CAUTION")
        # Send critical alert that override was used
        send_override_alert()
    
data_quality_checks >> BranchPythonOperator(
    task_id='quality_gate',
    python_callable=check_quality_and_continue
) >> daily_reports
