## Part 1: Failure Scenario Analysis

### Scenario 1: API Rate Limit (HTTP 429)

**Classification:** Transient
**Reasoning:** Rate limits are temporary by definition. The API explicitly tells us to retry after 60 seconds. The limit resets automatically — no human action needed.

**Retry Configuration:**
- retries: 3
- retry_delay: timedelta(minutes=2)
- retry_exponential_backoff: True
- max_retry_delay: timedelta(minutes=10)

**Why these values:**
- 3 retries gives the rate limit 3 windows to reset (2 min, 4 min, 8 min)
- Exponential backoff avoids hitting the limit again immediately
- max_retry_delay of 10 min prevents excessive waiting
- Total max wait: ~14 minutes — acceptable for a nightly job

**Alert Configuration:**
- Severity: P3 (Medium)
- Channel: Slack #data-alerts
- When to alert: Only after ALL 3 retries are exhausted
- Message template: "extract_product_catalog failed after 3 retries due to API rate limit (HTTP 429). Vendor API may be experiencing unusual load. Check vendor status page and consider reducing request concurrency."

**Runbook:**
1. Check the Airflow task logs for the 429 response and Retry-After header value
2. Check the vendor API status page for known rate limit changes
3. If rate limit was recently lowered, update DAG to reduce request concurrency
4. Manually trigger the task — if it succeeds, the rate limit has reset
5. If it keeps failing, contact the vendor about increasing your rate limit quota

### Scenario 2: Database Connection Timeout

**Classification:** Transient
**Reasoning:** Database connection timeouts during maintenance windows are temporary. The cluster auto-recovers within 5-10 minutes without human intervention.

**Retry Configuration:**
- retries: 4
- retry_delay: timedelta(minutes=3)
- retry_exponential_backoff: True
- max_retry_delay: timedelta(minutes=15)

**Why these values:**
- 4 retries covers typical 5-10 minute maintenance window (3, 6, 12, 15 min)
- Exponential backoff prevents hammering the recovering cluster
- max_retry_delay of 15 min caps wait but still allows recovery
- Total max wait: ~36 minutes — cluster should be recovered by then

**Alert Configuration:**
- Severity: P3 (Medium)
- Channel: Slack #data-alerts
- When to alert: After all retries exhausted OR after 2 consecutive failures (if recurring)
- Message template: "load_to_warehouse failed after 4 retries due to Redshift connection timeout. Cluster may be in maintenance or experiencing load. Check Redshift console and cluster metrics."

**Runbook:**
1. Check Redshift console for maintenance windows or cluster load
2. Review CloudWatch metrics for CPU utilization and connection count
3. Verify other Redshift-dependent DAGs are also failing (wider issue?)
4. If maintenance is ongoing, wait for completion and manually retry
5. If no maintenance, check security groups and network ACLs

### Scenario 3: Invalid Data Schema (Missing Column)

**Classification:** Permanent
**Reasoning:** No amount of retrying will add the missing column. The partner changed their export format without notice. Requires human intervention to fix schema or contact partner.

**Retry Configuration:**
- retries: 0
- retry_delay: N/A
- retry_exponential_backoff: N/A
- max_retry_delay: N/A

**Why these values:**
- Retries would waste resources and delay alerting
- The error will repeat exactly the same way
- Immediate human investigation is required

**Alert Configuration:**
- Severity: P1 (Critical)
- Channel: PagerDuty + Slack #data-incidents
- When to alert: Immediately (first failure)
- Message template: "CRITICAL: Partner data schema mismatch. Missing column 'transaction_amount' in partner file. Financial reports depend on this column. Contact partner immediately and update schema validation."

**Runbook:**
1. Check the exact error message to identify missing column
2. Contact the partner to notify them of schema mismatch
3. Request corrected file with all required columns
4. If partner cannot resend, update validation task to handle new schema
5. Manually reprocess the affected day's data once issue is resolved
6. Document the schema change for future reference

### Scenario 4: S3 Bucket Permission Denied

**Classification:** Permanent
**Reasoning:** The IAM role permissions were revoked during security audit. Retrying will produce the same AccessDenied error until IAM policy is restored by human action.

**Retry Configuration:**
- retries: 0
- retry_delay: N/A
- retry_exponential_backoff: N/A
- max_retry_delay: N/A

**Why these values:**
- Permission issues require human intervention
- Retries would waste compute resources
- Immediate alert needed to restore access

**Alert Configuration:**
- Severity: P1 (Critical)
- Channel: PagerDuty + Slack #data-incidents
- When to alert: Immediately (first failure)
- Message template: "CRITICAL: S3 AccessDenied error in archive_processed_files. IAM role missing write permission to archive bucket. Security audit may have revoked permissions. Restore IAM policy immediately to prevent data loss."

**Runbook:**
1. Check the exact error message for bucket name and operation
2. Contact security team about recent IAM policy changes
3. Request restoration of s3:PutObject permission for the service role
4. Verify permissions after restoration by manual test
5. Rerun failed tasks once access is restored

### Scenario 5: Network Partition (Intermittent Connectivity)

**Classification:** Transient
**Reasoning:** Network blips that self-resolve within ~15 minutes are temporary. The connection reset by peer indicates brief instability, not permanent failure.

**Retry Configuration:**
- retries: 4
- retry_delay: timedelta(minutes=2)
- retry_exponential_backoff: True
- max_retry_delay: timedelta(minutes=20)

**Why these values:**
- Network issues often resolve within 5-15 minutes
- 4 retries cover 2, 4, 8, 16 minute intervals (total ~30 minutes)
- Exponential backoff gives network time to stabilize
- max_retry_delay prevents waiting too long if network is truly down

**Alert Configuration:**
- Severity: P3 (Medium)
- Channel: Slack #data-alerts
- When to alert: After all retries exhausted OR escalate to P2 if multiple DAGs affected
- Message template: "sync_to_datalake failed after 4 retries due to network connectivity issues. Connection reset by peer when uploading to S3. Check network stability between on-prem and AWS."

**Runbook:**
1. Check network monitoring tools for connectivity metrics
2. Verify if other on-prem to cloud tasks are also failing
3. Contact network team if issue persists across multiple DAGs
4. If network recovers, manually retry failed tasks
5. Document incident for network reliability tracking

### Scenario 6: Data Quality Check Fails (Excessive Nulls)

**Classification:** Permanent
**Reasoning:** The data itself is bad — 35% nulls in email column indicates source system bug. Retrying the check will produce same result because data hasn't changed. Requires source system fix and data backfill.

**Retry Configuration:**
- retries: 0
- retry_delay: N/A
- retry_exponential_backoff: N/A
- max_retry_delay: N/A

**Why these values:**
- Data quality issues require investigation and source system fix
- Retries would waste resources and delay notification
- Marketing campaigns depend on this data — immediate alert needed

**Alert Configuration:**
- Severity: P1 (Critical)
- Channel: PagerDuty + Slack #data-incidents
- When to alert: Immediately (first failure)
- Message template: "CRITICAL: Data Quality Check Failed — Column 'email' null rate is 35.2%, exceeding 10% threshold. Source system bug detected. Marketing campaigns affected. Contact source system owners immediately."

**Runbook:**
1. Verify the exact null rate and affected columns from logs
2. Contact source system team to identify bug causing missing emails
3. Request timeline for source fix and data backfill
4. Once source fixed, trigger backfill of affected dates
5. Rerun data quality check on backfilled data
6. Notify stakeholders when data is clean and ready for use

## Part 2: Default Retry Policy

### Company Default Retry Policy

### default_args Configuration

```python
default_args = {
    "retries": 3,
    "retry_delay": timedelta(minutes=2),
    "retry_exponential_backoff": True,
    "max_retry_delay": timedelta(minutes=15),
}


### Justification

| Parameter | Value | Why |
|-----------|-------|-----|
| retries | 3 | Balances between giving enough chances for recovery and not delaying failure detection too long. Most transient issues resolve within 3 attempts. |
| retry_delay | timedelta(minutes=2) | Initial wait of 2 minutes gives brief hiccups time to self-resolve without excessive delay. Short enough for time-sensitive pipelines. |
| retry_exponential_backoff | True | Prevents hammering recovering systems and spreads out retries intelligently. Standard best practice for distributed systems. |
| max_retry_delay | timedelta(minutes=15) | Caps maximum wait at 15 minutes to prevent tasks from waiting too long. Balances between allowing recovery and failing fast. |


### Override Guidelines

| Scenario | Override | Reason |
|----------|----------|--------|
| Known permanent failures | retries=0 | Don't waste time retrying errors that require human intervention |
| API calls with rate limits | retries=3, retry_delay=2min | Respect rate limit windows and API provider guidance |
| Critical path tasks | retries=5, max_retry_delay=60min | Extra resilience for jobs that must complete |
| Tasks with external dependencies | retries=4 | More chances for external system recovery |
| Short-running time-sensitive tasks | retries=2, retry_delay=30s | Fail faster to allow alternate paths or manual intervention |
| Long-running batch jobs | retries=3, max_retry_delay=30min | Balance between completion and resource usage |
