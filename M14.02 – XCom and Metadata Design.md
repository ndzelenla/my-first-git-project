## Part 1: XCom vs External Storage Classification

| # | Data Item | Size Estimate | Classification | Reasoning |
|---|-----------|---------------|----------------|-----------|
| 1 | Row count from an extract task (e.g., `1500`) | ~10 bytes | XCom | Tiny integer, classic metadata under 1KB |
| 2 | File path string (e.g., `s3://bucket/data/2025-06-15/output.parquet`) | ~60 bytes | XCom | Short string pointing to where data lives, under 1KB |
| 3 | A Pandas DataFrame with 100K rows and 20 columns | ~10 MB | External Storage | Too large for metadata DB (>1KB), actual data not metadata |
| 4 | Partition date string (e.g., `2025-06-15`) | ~10 bytes | XCom | Tiny string, essential pipeline metadata |
| 5 | Error message from a failed validation (e.g., `"Column 'email' has 15 nulls"`) | ~50 bytes | XCom | Short diagnostic string, under 1KB |
| 6 | Model accuracy score (e.g., `0.94`) | ~8 bytes | XCom | Single float value, under 1KB |
| 7 | Full SQL query results (50K rows, 10 columns) | ~25 MB | External Storage | Large dataset, not metadata (>1KB) |
| 8 | S3 bucket name (e.g., `my-data-lake-prod`) | ~20 bytes | XCom | Short configuration string, under 1KB |
| 9 | Customer list with 50,000 records (JSON array) | ~15 MB | External Storage | Large payload (>1KB), use S3/GCS instead |
| 10 | Status flag (e.g., `"success"` or `"failure"`) | ~8 bytes | XCom | Tiny enum-like value, under 1KB |
| 11 | Configuration JSON with 3 key-value pairs | ~50 bytes | XCom | Small config object, under 1KB |
| 12 | Processed CSV file contents (full text of a 500-row CSV) | ~200 KB | External Storage | File contents should be stored as files, pass the path instead |

## Part 2: XCom Key Design for ETL Pipeline

### Naming Convention
All XCom keys follow the pattern: `{task_name}_{data_description}`

### XCom Contract

| XCom Key | Value Type | Example Value | Producer | Consumer(s) |
|----------|-----------|---------------|----------|-------------|
| `extract_row_count` | int | `1500` | extract | validate, notify |
| `extract_file_path` | string | `s3://bucket/raw/2025-06-15/data.parquet` | extract | validate |
| `extract_timestamp` | string | `2025-06-15T03:22:41Z` | extract | notify |
| `validate_status` | string | `"passed"` or `"failed"` | validate | transform, notify |
| `validate_error_count` | int | `0` | validate | transform, notify |
| `validate_error_summary` | string | `"No errors found"` or `"3 nulls in email column"` | validate | notify |
| `transform_output_path` | string | `s3://bucket/cleaned/2025-06-15/transformed.parquet` | transform | load, notify |
| `transform_row_count` | int | `1495` | transform | load, notify |
| `transform_columns_added` | int | `2` | transform | notify |
| `transform_column_names` | list | `["email_domain", "age_group"]` | transform | notify |
| `load_table_name` | string | `"revenue_fact"` | load | notify |
| `load_rows_inserted` | int | `1495` | load | notify |
| `load_duration_seconds` | float | `12.5` | load | notify |
| `load_status` | string | `"success"` | load | notify |

### Design Questions

1. **Why does `notify` consume from almost every task?**

| Question | Answer |
|----------|--------|
| Why does notify consume from almost every task? | The notify task is responsible for sending a comprehensive summary of the entire pipeline execution. It needs metadata from all stages to report on what was extracted, validation results, transformation details, and load statistics. This allows stakeholders to understand the full ETL outcome in one notification. |

2. **Should `validate_error_summary` be a string or a list? What are the trade-offs?**

| Question | Answer |
|----------|--------|
| Should validate_error_summary be a string or a list? | **String vs List Trade-offs:** String is simpler and guaranteed to be serializable, but loses structure. List preserves structure (can iterate through individual errors), but increases size and complexity. For this case, **string** is better because: (1) error summary is meant for human reading in notifications, (2) lists with many errors could exceed XCom size limits, (3) detailed errors should be logged separately. |

3. **What happens if `extract` fails and pushes no XCom values? How should `validate` handle this?**

| Question | Answer |
|----------|--------|
| What happens if extract fails? | If extract fails, downstream tasks like validate will receive None from xcom_pull calls. Validate should: (1) Check for None values on all expected XCom keys, (2) Raise clear exceptions with meaningful error messages, (3) Not attempt to proceed with missing data. The DAG should fail fast with clear indication that extract failed. |

4. **Could you replace all individual XCom keys with a single JSON dict per task? Pros and cons?**

| Question | Answer |
|----------|--------|
| Replace with single JSON dict per task? | **Pros:** Reduces number of XCom entries, cleaner contract between tasks, easier to version metadata structure, fewer database lookups. **Cons:** Harder to track dependencies at task level in Airflow UI, consumers may need only subset but still pull entire object, risk of exceeding size limits if dict grows too large. |

### XCom Data Flow
extract ──┬── extract_row_count ──────→ validate, notify
├── extract_file_path ──────→ validate
└── extract_timestamp ──────→ notify

validate ─┬── validate_status ────────→ transform, notify
├── validate_error_count ───→ transform, notify
└── validate_error_summary ─→ notify

transform ─┬── transform_output_path ─→ load, notify
├── transform_row_count ───→ load, notify
├── transform_columns_added → notify
└── transform_column_names ─→ notify

load ──────┬── load_table_name ───────→ notify
├── load_rows_inserted ────→ notify
├── load_duration_seconds ─→ notify
└── load_status ───────────→ notify

## Part 3: Identify XCom Anti-Patterns

### Anti-Pattern 1: Pushing a DataFrame

**What's wrong:**
Pushing an entire 100K-row DataFrame (10+ MB) to XCom.

**Why it's dangerous:**
XCom stores data in Airflow's metadata database. Large objects: (1) bloat the database, (2) slow down the Airflow UI and scheduler, (3) can exceed database field size limits, (4) cause excessive serialization/deserialization overhead.

**Corrected code:**
```python
# Task: extract_data
def extract_data(**context):
    df = pd.read_csv("s3://bucket/raw/transactions.csv")  # 100K rows
    
    # Save to S3 instead of pushing to XCom
    output_path = "s3://bucket/processed/2025-06-15/extracted.parquet"
    df.to_parquet(output_path)
    
    # Push ONLY metadata to XCom
    context["ti"].xcom_push(key="extract_output_path", value=output_path)
    context["ti"].xcom_push(key="extract_row_count", value=len(df))
    
    print(f"Saved {len(df)} rows to {output_path}")



## Anti-Pattern 2: Pushing Large Query Results
What's wrong:
Pushing 50,000 customer records (50 MB JSON) to XCom.

Why it's dangerous:
Massive serialization time, huge strain on metadata database storage, network transfer overhead between scheduler and workers, risk of hitting database field size limits.

Corrected code:

python
# Task: run_query
def run_query(**context):
    results = database.execute("SELECT * FROM customers WHERE region = 'US'")
    
    # Write results to a file/table
    output_path = "s3://bucket/query_results/us_customers.json"
    save_results_to_s3(results, output_path)
    
    # Push ONLY the reference and metadata
    context["ti"].xcom_push(key="query_results_path", value=output_path)
    context["ti"].xcom_push(key="query_row_count", value=len(results))
    
    print(f"Saved {len(results)} customer records to {output_path}")


## Anti-Pattern 3: Not Handling Missing XCom
What's wrong:
Using xcom_pull results without checking for None values.

Why it's dangerous:
If upstream task fails or doesn't push the expected key, xcom_pull returns None. This causes cryptic errors downstream (like TypeError when trying to use None as string) instead of clear failure messages.

Corrected code:

python
# FIXED: Transform with proper XCom handling
def transform_data(**context):
    row_count = context["ti"].xcom_pull(task_ids="extract", key="row_count")
    
    if row_count is None:
        raise ValueError(
            "XCom key 'row_count' not found from task 'extract'. "
            "Did the extract task complete successfully?"
        )
    
    file_path = context["ti"].xcom_pull(task_ids="extract", key="file_path")
    
    if file_path is None:
        raise ValueError(
            "XCom key 'file_path' not found from task 'extract'. "
            "The extract task may have failed before pushing this value."
        )
    
    print(f"Processing {row_count} rows from {file_path}")
    df = pd.read_csv(file_path)


## Anti-Pattern 4: Tight Coupling via Excessive XCom
What's wrong:
Task B depends on 5 different XCom keys from Task A, creating tight coupling.

Why it's dangerous:
Changing Task A's XCom keys breaks Task B; hard to test Task B independently; difficult to refactor either task; Task B "knows" too much about Task A's internal implementation details.

Corrected approach:

python
# FIXED: Reduce coupling with a structured metadata dict
def task_a(**context):
    # Push a single structured metadata object
    metadata = {
        "source_path": "s3://bucket/data/2025-06-15/output.parquet",
        "row_count": 1500,
        "partition_date": "2025-06-15"
    }
    context["ti"].xcom_push(key="task_a_output", value=metadata)
 
def task_b(**context):
    # Pull one key instead of five
    metadata = context["ti"].xcom_pull(task_ids="task_a", key="task_a_output")
    
    if metadata is None:
        raise ValueError("No output metadata from task_a")
    
    process_data(
        source_path=metadata["source_path"],
        row_count=metadata["row_count"],
        partition_date=metadata["partition_date"]

#############   Anti-Pattern Summary
| # | Anti-Pattern | Root Cause | Fix |
|---|-------------|-----------|-----|
| 1 | Pushing DataFrame via XCom | Treating XCom as data storage | Save to S3, push path |
| 2 | Pushing large JSON (50MB) | No size awareness | Write to file/table, push reference |
| 3 | No null check on xcom_pull | Assuming upstream always succeeds | Explicit None checks with clear errors |
| 4 | 5+ XCom keys = tight coupling | Task knows too much about another | Consolidate into structured metadata dict |
