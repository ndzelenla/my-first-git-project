## Module: M16.01 – Distributed Systems Scalability Analysis

## Executive Summary

This audit assessed five core pipelines against current infrastructure capacity and projected 30% annual data growth. **Pipeline A (Daily Play Counts)** and **Pipeline B (User Recommendations)** present immediate critical risks due to memory exhaustion and batch window violation, respectively. **Pipeline D (Revenue Attribution)** requires short-term optimization to prevent failure within 12 months. Pipelines C and E are stable and do not require distributed computing. A phased migration roadmap prioritizing Spark adoption for high-risk pipelines is recommended to ensure system reliability and headroom for growth.

## Pipeline Analysis

### Pipeline A: Daily Play Counts

**Description:** Aggregates 80M daily plays into a top 1,000 songs list for marketing.

| Metric | Current | +1 Year (30% growth) | +2 Years |
| :--- | :--- | :--- | :--- |
| **Daily Rows** | 80 Million | 104 Million | 135 Million |
| **File Size** | 12 GB | 15.6 GB | 20.3 GB |
| **Peak Memory** | 58 GB | ~75 GB | ~98 GB |
| **Runtime** | 2.5 hours | ~3.25 hours | ~4.2 hours |

**Bottleneck:** **Memory** (58 GB / 64 GB = 91% utilization).
**Risk Level:** **CRITICAL**
**Reason:** Current memory usage is dangerously close to the physical limit. Projected 30% growth will push memory demand to ~75 GB within one year, exceeding capacity and causing `MemoryError` failures.

**Recommendation:**
*   **Immediate (Quick Win):** Optimize Pandas read. Read only the three required columns (`song_id`, `artist_id`, `played_at`) instead of the entire 15-column CSV. This could reduce memory footprint to ~12 GB.
    ```python
    # Current: df = pd.read_csv('plays.csv') # Loads all 15 columns
    # Optimized:
    df = pd.read_csv('plays.csv', usecols=['song_id', 'artist_id', 'played_at'])
    ```
*   **Short-term (This Sprint):** Migrate this pipeline to run on a **Spark local mode** cluster on the same server. This will allow data to be processed in memory across multiple cores more efficiently and handle the 20 GB+ file size expected next year.
*   **Medium-term:** Move to a proper **Spark cluster** (e.g., Databricks, EMR) when data volume consistently exceeds 25 GB.

### Pipeline B: User Recommendation Model

**Description:** Scores 5 million active users against a collaborative filtering model to generate personalized playlists.

| Metric | Current |
| :--- | :--- |
| **Input Data** | 5M users x 200 features (1B values) |
| **Processing** | Sequential Python/NumPy loop |
| **Runtime** | **9 hours** |
| **Memory Usage** | 22 GB (peak) |

**Bottleneck:** **Compute** (CPU-bound due to sequential user processing).
**Risk Level:** **CRITICAL**
**Reason:** The pipeline already **exceeds the 6-hour batch window by 3 hours (50% over time)** . The sequential loop over 5 million users does not scale. Adding more RAM will not solve this, as the bottleneck is processing time, not memory capacity.

**Recommendation:**
*   **Immediate (This Sprint):** Parallelize the user scoring loop. The task is "embarrassingly parallel" – users can be scored independently.
    *   **Option A (Quick, limited):** Use Python's `multiprocessing.Pool` to distribute users across the 16 available CPU cores. This could reduce runtime to ~1-2 hours temporarily.
    *   **Option B (Strategic):** Migrate immediately to **PySpark** on a cluster. Spark's distributed `map` or `mapPartitions` is the ideal pattern for this use case, allowing scoring across hundreds of cores.
*   **Long-term:** Implement a model-serving layer (e.g., with MLflow on Spark) to generate recommendations incrementally or in near-real-time.

### Pipeline C: Song Metadata Sync

**Description:** Fetches new/updated song metadata (2k-5k records daily) from a partner API and upserts to PostgreSQL.

| Metric | Current |
| :--- | :--- |
| **Data Size** | ~50 MB |
| **Processing** | Sequential API calls |
| **Runtime** | 25 minutes |
| **Memory Usage** | 200 MB |

**Bottleneck:** **I/O** (Network latency from sequential API calls).
**Risk Level:** **LOW**
**Reason:** Data volume is negligible (50 MB). Runtime (25 min) is well within the 6-hour batch window. Even with 30% annual growth, this pipeline will remain trivial for the next 3-5 years.

**Recommendation:**
*   **No Migration Needed.**
*   **Optimization (Optional):** Increase page size in API requests to reduce the number of sequential calls. Implement simple `asyncio` or `ThreadPoolExecutor` for parallel fetches if API rate limits allow, but this is not urgent.

### Pipeline D: Revenue Attribution

**Description:** Joins plays (12 GB), subscriptions (2 GB), and payments (1 GB) to calculate per-artist/song royalties for finance.

| Metric | Current | +1 Year (30% growth) |
| :--- | :--- | :--- |
| **Total Data** | 15 GB | ~19.5 GB |
| **Processing** | Pandas chunked read + merge |
| **Runtime** | 4.5 hours | ~5.9 hours |
| **Memory (Peak)** | 52 GB | ~68 GB |

**Bottleneck:** **Memory** (Join operation causes memory spike to 81% of capacity).
**Risk Level:** **HIGH**
**Reason:** The join between the large `plays` and `subscriptions` DataFrames creates an intermediate structure that temporarily balloons memory to 52 GB. With 30% data growth, this join will exceed the 64 GB limit within 12-15 months, and runtime will begin to encroach on the 6-hour batch window.

**Recommendation:**
*   **Short-term (Next 2 Sprints):**
    1.  **Pushdown Joins to SQL:** Instead of loading all three tables into Pandas and joining in memory, perform the join directly in **PostgreSQL** using a SQL query. Only bring the final, filtered result set into Pandas for the per-play revenue calculation. This leverages the database's optimized join engine.
    2.  **Column Pruning:** Select only the necessary columns for the join and calculation, reducing data shuffled.
*   **Medium-term (Next Quarter):** Migrate the entire pipeline to **Spark**. Spark's optimizer handles large joins more gracefully than Pandas by spilling to disk if necessary and distributing the join across a cluster.

### Pipeline E: A/B Test Analytics

| Metric | Current |

| **Runtime** | 8 minutes per test |
| **Memory Usage** | 3 GB (peak) |

**Bottleneck:** **None** (Well within all limits).
**Risk Level:** **LOW**
**Reason:** The pipeline handles small data volumes (1.5 GB total) efficiently. Runtime (8 min per test) is minimal. The workload is perfectly suited for single-node Pandas and SciPy.

**Recommendation:**
*   **No Migration Needed.** This is an example of a pipeline that should remain on the current stack indefinitely. Introducing distributed computing would add unnecessary complexity and overhead with zero benefit.

## Migration Priority Roadmap

### Priority 1 — Immediate (This Sprint)
*   **Pipeline:** A (Daily Play Counts) & B (User Recommendations)
*   **Reason:** Both are **critical risks**. Pipeline A will hit a hard memory wall within months. Pipeline B is already breaking the SLA by exceeding the batch window by 50%. Failure is imminent.
*   **Action:**
    *   **A:** Implement column pruning immediately. Begin setup of a Spark environment (e.g., a small Databricks cluster or local Spark mode) and migrate the aggregation logic.
    *   **B:** Immediately parallelize the user scoring loop using `multiprocessing` as a band-aid, while concurrently building the PySpark version for a production-grade fix.

### Priority 2 — Short-term (Next 2 Sprints)
*   **Pipeline:** D (Revenue Attribution)
*   **Reason:** **High risk**. While not failing today, the join memory pressure and runtime will become critical within one year given 30% growth. Proactive refactoring is cheaper than emergency firefighting.
*   **Action:** Refactor the pipeline. Move the large table joins into SQL (pushdown) to run inside PostgreSQL. Only bring the aggregated results into Python. Monitor performance gains.

### Priority 3 — Medium-term (Next Quarter)
*   **Pipeline:** D (Revenue Attribution)
*   **Reason:** Even with SQL pushdown, the underlying data volume will eventually outgrow a single-node database for this complex join pattern.
*   **Action:** Complete the migration of Pipeline D to the Spark cluster established for Pipelines A and B, ensuring a unified, scalable processing platform for all high-volume workloads.

### No Migration Needed
*   **Pipelines:** C (Song Metadata Sync) & E (A/B Test Analytics)
*   **Reason:** These pipelines handle small data volumes efficiently within the current single-node environment. They do not present a scalability risk for the foreseeable future. They should remain on Pandas/PostgreSQL to avoid the operational overhead of distributed systems where it provides no value.
