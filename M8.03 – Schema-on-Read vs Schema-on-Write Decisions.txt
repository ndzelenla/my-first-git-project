Step 3: Batch vs Streaming (10 mins)

=====================================================================================================================================
| ASPECT                  | BATCH PROCESSING                                      | STREAMING PROCESSING                                  |
|=========================|=======================================================|======================================================|
| DEFINITION              | Processing data in large, discrete chunks            | Processing data continuously in real-time            |
|                         | at scheduled intervals (hourly, daily, weekly)       | as it arrives (milliseconds to seconds)             |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| PROCESSING WINDOW       | Fixed, scheduled intervals                           | Continuous, always-on                               |
|                         | Example: "Run every night at 2 AM"                   | Example: "Process as events arrive"                 |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| DATA VOLUME PER RUN     | Large (GB to PB)                                     | Small (bytes to KB per event)                       |
|                         | Processes all data accumulated since last run        | Processes individual events or micro-batches        |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| LATENCY                 | High (minutes to hours)                              | Low (milliseconds to seconds)                       |
|                         | Data is "cold" by time it's processed                | Data is "hot" - near real-time                      |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| COMPUTE PATTERN         | Start, process, stop, release resources              | Always running, continuous processing               |
|                         | Ephemeral clusters                                   | Long-running services                               |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
|================================================|=======================================================|
| SCHEMA STRATEGY IN BATCH VS STREAMING          |                                                       |
|================================================|=======================================================|
| DEFAULT SCHEMA APPROACH  | SCHEMA-ON-WRITE (preferred)                        | SCHEMA-ON-READ (preferred)                         |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| SCHEMA TIMING           | Schema applied before/during processing             | Schema applied at query time                        |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| VALIDATION WINDOW       | Ample time - can validate every record              | Minimal time - can't afford per-record validation   |
|                         | Full ACID compliance possible                       | Must trade accuracy for speed                       |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| SCHEMA EVOLUTION        | Planned, coordinated changes                        | Continuous, organic evolution                       |
|                         | Versioned migrations                                | New fields appear automatically                     |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| ERROR HANDLING          | Dead letter queue, reprocess entire batch           | Skip bad events, alert, continue                    |
|                         | "Fail fast, fix, restart"                           | "Tolerate, monitor, fix later"                      |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| DATA REPROCESSING       | Easy - just rerun the batch                         | Difficult - events are transient                    |
|                         |                                                 | Must replay from source or store raw               |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
|================================================|=======================================================|
| CONSIDERATIONS                                 |                                                       |
|================================================|=======================================================|
| STRENGTHS              | • Complete, accurate results                        | • Immediate insights                                |
|                         | • Easier to reason about correctness                | • Real-time alerts and actions                      |
|                         | • Efficient for large aggregations                  | • Lower latency, better UX                          |
|                         | • Simpler exactly-once semantics                    | • Can handle unbounded data                         |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| CHALLENGES             | • High latency - data is stale                      | • Complex exactly-once semantics                    |
|                         | • Infrastructure idle between runs                  | • State management is difficult                     |
|                         | • Inefficient for real-time needs                   | • Backpressure handling                             |
|                         | • Growing batch windows as data grows               | • Out-of-order events                               |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|
| SCHEMA CHALLENGES      | • Schema changes require backfill                   | • Schema-less leads to "schema drift"               |
|                         | • Long-running migrations                           | • Readers must handle many versions                 |
|                         | • Testing schema changes on petabytes               | • Difficult to enforce contracts                    |
|-------------------------|-------------------------------------------------------|------------------------------------------------------|

| HOW BATCH VS STREAMING AFFECTS SCHEMA DECISIONS                                                                                  |
|====================================================================================================================================|
| DECISION FACTOR        | BATCH IMPACT                                         | STREAMING IMPACT                                     |
|------------------------|------------------------------------------------------|------------------------------------------------------|
| SCHEMA ENFORCEMENT     | Can enforce strict schema at load                  | Must be permissive; can't block on bad data        |
|                        | "Bad data" can be rejected, quarantined            | "Bad data" must be tolerated, flagged              |
|------------------------|------------------------------------------------------|------------------------------------------------------|
| VALIDATION COMPLEXITY  | Complex validation possible (joins, lookups)       | Simple validation only (format, required fields)   |
|                        | Full referential integrity checks                  | Async enrichment preferred                         |
|------------------------|------------------------------------------------------|------------------------------------------------------|
| SCHEMA EVOLUTION       | Versioned schemas with migration scripts           | Schema registry with compatibility modes           |
|                        | Backward/forward compatibility managed             | Reader must handle multiple versions               |
|------------------------|------------------------------------------------------|------------------------------------------------------|
| DATA QUALITY           | High quality expected; clean before load           | Variable quality; clean after query                |
|                        | "Trust but verify"                                 | "Verify at read time"                              |
|------------------------|------------------------------------------------------|------------------------------------------------------|
| TRANSFORMATION PATTERN | ELT or ETL                                         | Stream processing + enrichment                     |
|                        | Transform after loading or before                  | Transform in-flight                                |

| • Simpler to reason about correctness                | • Better customer experience                        |
| • Efficient for large aggregations                   | • Can handle unbounded data streams                 |
| • Mature tooling and practices                       | • Natural fit for event-driven architectures       |
| • Easier compliance and auditing                     | • Reduced infrastructure idle time                  |
|-------------------------------------------------------|------------------------------------------------------|
| BATCH DISADVANTAGES                                  | STREAMING DISADVANTAGES                             |
|-------------------------------------------------------|------------------------------------------------------|
| • High latency - data is stale by definition         | • Complex exactly-once semantics                    |
| • Inefficient for time-sensitive decisions           | • State management is hard                          |
| • Growing batch windows become unmanageable          | • Schema drift is constant challenge                |
| • Resource idle between runs                         | • More complex operations                          |

| DECISION FRAMEWORK: BATCH VS STREAMING        |                                                  |                                          |
|================================================|==================================================|==========================================|
| ASK THESE QUESTIONS:                          | BATCH IF:                                       | STREAMING IF:                           |
|-----------------------------------------------|--------------------------------------------------|------------------------------------------|
| How fresh must the data be?                  | Minutes to hours is acceptable                 | Milliseconds to seconds required        |
|-----------------------------------------------|--------------------------------------------------|------------------------------------------|
| What is the event volume?                   | Predictable, scheduled bursts                 | Continuous, unpredictable peaks         |
|-----------------------------------------------|--------------------------------------------------|------------------------------------------|
| Is the data bounded or unbounded?           | Bounded (yesterday's data)                    | Unbounded (events keep coming)          |
|-----------------------------------------------|--------------------------------------------------|------------------------------------------|
| What actions depend on this?                | Reports, planning, strategy                   | Alerts, offers, fraud blocks            |
|-----------------------------------------------|--------------------------------------------------|------------------------------------------|
| What are the quality requirements?          | 100% accurate, auditable                      | "Good enough" for immediate action      |
|-----------------------------------------------|--------------------------------------------------|------------------------------------------|

|                                                                                                                                   |
|   • Use BATCH when you need to be RIGHT.                                                                                         |
|   • Use STREAMING when you need to be FAST.                                                                                      |
|   • Use HYBRID when you need to be BOTH.                                                                                         |
|                                                                                                                                   |
|   Schema strategy follows naturally:                                                                                             |
|   • BATCH processes the past → Schema-on-Write for accuracy                                                                      |
|   • STREAMING processes the present → Schema-on-Read for speed                                                                   |
|   • HYBRID bridges both → Multi-schema strategy                                                                                  |

|=====================================================================================================================================
| SUMMARY: PRINCIPLES TO LIVE BY                                                                                                    |
|=====================================================================================================================================
|                                                                                                                                   |
|   ⚖️  THE GOLDEN RULE:                                                                                                           |
|      "Schema-on-write for systems of record where data MUST be correct.                                                          |
|       Schema-on-read for systems of engagement where data MUST be fast.                                                           |
|       Hybrid for enterprises that need BOTH."                                                                                    |
|                                                                                                                                   |
|   🎯 THE 80/20 PRINCIPLE:                                                                                                        |
|      80% of your data doesn't need strict schema enforcement.                                                                     |
|      20% (transactional, financial, compliance) absolutely does.                                                                  |
|      Apply strict control only where the cost of error exceeds the cost of control.                                               |
|                                                                                                                                   |
|   🔄 THE EVOLUTION PRINCIPLE:                                                                                                    |
|      Start flexible (schema-on-read), add structure as patterns emerge.                                                          |
|      Don't over-design for unknown future use cases.                                                                             |
|      Let usage patterns drive schema decisions.                                                                                  |                                             |
|      When contract is "best effort" → Schema-on-read.                                                                            |
|                                                                                                                                   |
|=====================================================================================================================================
| FINAL VERDICT                                                                                                                     |
|=====================================================================================================================================
|                                                                                                                                   |
|   "There is no single correct answer. There is only the right answer for YOUR context.                                           |
|                                                                                                                                   |
|    • Banking transactions → Schema-on-write. Period. No debate.                                                                  |
|    • IoT sensor readings → Schema-on-read. Anything else is too slow.                                                            |
|    • Everything else → It depends.                                                                                               |
|                                                                                                                                   |
|    The mark of a senior data architect is not knowing which is better,                                                            |
|    but knowing which is better for THIS specific problem."                                                                        |
