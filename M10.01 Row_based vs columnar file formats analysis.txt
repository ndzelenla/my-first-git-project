|-----------------------|-------------------------------------------------------|---------------------------------------|

|-----------------------|-------------------------------------------------------|---------------------------------------|
| Write Pattern         | Fast for single-row inserts/updates                   | Slower for writes, requires           |
|                       |                                                       | reorganizing multiple column files    |
|-----------------------|-------------------------------------------------------|---------------------------------------|
| Compression           | Limited (mixed data types per block)                  | Excellent (same data types, similar   |
|                       |                                                       | values together)                      |
|-----------------------|-------------------------------------------------------|---------------------------------------|
| Analytics Performance | Poor - scans unnecessary data                         | Excellent - reads only relevant        |
|                       |                                                       | columns                               |
|-----------------------|-------------------------------------------------------|---------------------------------------|
| Transaction           | Excellent - optimized for point queries               | Poor - overhead of reconstructing     |
| Performance           |                                                       | rows                                  |
|-----------------------|-------------------------------------------------------|---------------------------------------|
| Best Use Case         | OLTP, CRUD operations, high-concurrency writes        | OLAP, data warehousing, big data      |
|                       |                                                       | analytics                             |
|-----------------------|-------------------------------------------------------|---------------------------------------|
| Example Query         | SELECT * FROM orders WHERE id = 123                   | SELECT SUM(sales) FROM orders         |
|                       |                                                       | GROUP BY region                       |
|-----------------------|-------------------------------------------------------|---------------------------------------|
| Data Skipping         | Minimal - must scan rows sequentially                 | Advanced - can skip entire column     |

|-----------------------|-------------------------------------------------------|---------------------------------------|
| Schema Evolution      | Flexible - easy to add columns                        | More complex - requires metadata      |
|                       |                                                       | updates                               |
|-----------------------|-------------------------------------------------------|---------------------------------------|
| Storage Size          | Larger (less compression)                             | Smaller (superior compression)        |

### Summary Notes (10 mins)
# Create a short summary:

Row-Based Formats (CSV, JSON, RDBMS) are preferred when:

-- Transactional Systems (OLTP)

-- Why: Need fast point queries, inserts, and updates on individual records

-- Real-world: Bank account system where you frequently query and update customer balances

-- Trade-off: Analytics queries will be slow and resource-intensive


CRUD Applications

--Why: Applications that create, read, update, and delete records need to access complete rows

--Real-world: E-commerce shopping cart, CRM system, inventory management

--Trade-off: Storage overhead is higher due to poor compression


Small to Medium Datasets (< 100GB)

--Why: Simplicity and flexibility outweigh performance benefits of columnar formats

--Real-world: Departmental spreadsheets, small business databases, application logs

--Trade-off: As data grows, performance will degrade


Frequently Updated Data

--Why: Updates can be done in-place on existing rows without rewriting entire files

--Real-world: User profile information, session data, real-time sensor readings

--Trade-off: Concurrent updates require careful locking mechanisms


Schema-Flexible Environments

--Why: Easy to add/remove columns without complex metadata management

--Real-world: Early-stage startups, prototype development, evolving data models

--Trade-off: Data quality and consistency may suffer


Full Row Exports/Imports

--Why: When you always need all columns for every record

--Real-world: Data migration between systems, backup/restore operations

--Trade-off: File sizes are larger than compressed columnar Formats


Columnar Formats (Parquet, ORC, Arrow) are preferred when:
Analytical Workloads (OLAP)

--Why: Only need to read specific columns for aggregations and calculations

--Real-world: Business intelligence dashboard showing sales by region and product

--Trade-off: Single-row operations are slow and inefficient


Large Datasets (> 100GB)

--Why: Columnar compression reduces storage by 5-20x, making large data manageable

--Real-world: Data warehouse with years of customer transaction history

--Trade-off: Initial data loading takes longer due to encoding Overhead


Aggregation-Heavy Queries

--Why: SUM, AVG, COUNT, GROUP BY operations only need specific columns

--Real-world: "Calculate average order value by customer segment for last quarter"

--Trade-off: SELECT * queries require reconstructing rows from multiple columns


Data Science & Machine Learning

--Why: ML training often uses subsets of columns; columnar enables efficient feature access

--Real-world: Training a recommendation model using user behavior features

--Trade-off: Need to convert to row-based for some ML libraries


Append-Only Workloads

--Why: Columnar formats optimize for batch writes, not updates

--Real-world: IoT sensor data streaming, clickstream logs, event tracking

--Trade-off: Updating historical data requires rewriting entire column files


Cost-Optimized Storage

--Why: Superior compression reduces cloud storage costs significantly

--Real-world: Storing years of log files in data lakes (S3, ADLS, GCS)

--Trade-off: CPU overhead for compression/decompression


Predicate Pushdown Scenarios

--Why: Can skip entire column blocks based on filter conditions

--Real-world: "Find all orders from 2024" - only reads date column blocks

--Trade-off: Requires metadata like min/max statistics per block
