-- For orders: Order Entity
- Selected Primary Key: order_id (Surrogate Key)
Why order_id?

Business Requirement: Orders need unique identifiers for tracking

Stability: Order IDs should never change once assigned

Simplicity: Single integer field, easy for customers to reference

-- For Products:
- Selected Primary Key: product_id (Surrogate Key)
Why product_id?

Stability: Internal ID never changes even if SKU changes

Performance: Integer joins faster than string-based SKU joins

Simplicity: Consistent with other entity keys

-- SKU as Natural Key - Why Not Primary?

Format Changes: SKU numbering schemes may evolve

Business Mergers: SKU formats might conflict during acquisitions

Length Issues: SKUs can be long strings (less efficient)

OrderItem → Order
- Relationship: One order can have many order items

OrderItem → Product

- Foreign key: OrderItem.product_id → Product.product_id
- Required: Yes (every order item must reference a product)

Composite Key Analysis (10 mins)
Why order_id + product_id is a composite key - In the OrderItem table, we need to track which products are in which orders. This is a classic many-to-many relationship

Explain why both columns are needed - Only One Product Per Order: Primary key constraint prevents adding multiple products to same order
What makes this combination unique - Uniqueness: Each product appears only once per order (quantity handles multiples)
Why a single column wouldn't work - Business Logic Violation: Orders typically contain multiple products
What breaks if only one column is used - Product Exclusivity: Each product can only appear in ONE order ever

What problems would occur with only order_id - Only One Product Per Order: Primary key constraint prevents adding multiple products to same order
What problems would occur with only product_id - Product Exclusivity: Each product can only appear in ONE order ever
Why the combination is necessary - The composite key (order_id, product_id) perfectly models the business rule:

Uniqueness: Each product appears only once per order (quantity handles multiples)

Table: orders_raw
order_id | customer_name | customer_city | product_name | product_price | quantity

Issues Identified:

Data Redundancy:

Customer information repeated for each order line

Product information repeated for each order line

Example: "John Smith, New York" appears 3 times

Example: "Laptop, 1200.00" appears 2 times
###############################################

Update Anomalies:

Update Problem: If customer "John Smith" moves to "Boston", need to update 3 rows

Risk of inconsistent data if some rows not updated
####################################

Insertion Anomalies:

Insert Problem: Cannot add a new customer without them placing an order

Cannot add a new product without it being ordered
#############################################

Deletion Anomalies:

Delete Problem: If order 1002 is deleted, lose information about product "Keyboard"

If last order for "Mouse" is deleted, lose product Information
##############################################

Atomicity Violation:

Combined customer, order, and product data in single table

Violates single responsibility principle for tables
#######################
functional dependencies identified
1. order_id → customer_name, customer_city
2. order_id, product_name → quantity, product_price
3. product_name → product_price
4. customer_name → customer_city (assuming name uniquely identifies customer)

Primary Key Candidate:
Composite Key: (order_id, product_name)

However, this still leaves normalization issues

Requirements for 1NF:
Each column contains atomic values (no repeating groups)

Each column has unique name

All values in a column are same data type

Current State Analysis:
The current table is already in 1NF because:

All columns contain atomic values

No repeating groups or arrays

Each column has unique name

Values are consistent data types

Second Normal Form (2NF) Normalized Schema
Requirements for 2NF:
Must be in 1NF

No partial dependencies (all non-key attributes fully dependent on entire primary key)

Partial Dependency Analysis:
For table with PK (order_id, product_name):

Full Dependencies (depend on entire PK):

quantity - depends on BOTH order_id AND product_name

Partial Dependencies (depend on part of PK):

customer_name, customer_city - depend only on order_id

product_price - depends only on product_name

-- Table 1: Orders (depends on order_id only)
CREATE TABLE orders_2nf (
    order_id INT PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL,
    customer_city VARCHAR(50) NOT NULL
);

-- Table 2: Products (depends on product_name only)
CREATE TABLE products_2nf (
    product_name VARCHAR(100) PRIMARY KEY,
    product_price DECIMAL(10, 2) NOT NULL
);

-- Table 3: OrderItems (depends on both order_id and product_name)
CREATE TABLE order_items_2nf (
    order_id INT NOT NULL,
    product_name VARCHAR(100) NOT NULL,
    quantity INT NOT NULL,
    PRIMARY KEY (order_id, product_name),
    FOREIGN KEY (order_id) REFERENCES orders_2nf(order_id),
    FOREIGN KEY (product_name) REFERENCES products_2nf(product_name)
);

Third Normal Form (3NF) Normalized Schema
Requirements for 3NF:
Must be in 2NF

No transitive dependencies (non-key attributes depend only on primary key)

Transitive Dependency Analysis:
In orders_2nf table:

PK: order_id

customer_name depends on order_id ✓

customer_city depends on customer_name (transitive) ❌

customer_city should depend directly on order_id, but it doesn't

-- Table 1: Customers (new table to eliminate transitive dependency)
CREATE TABLE customers_3nf (
    customer_id INT PRIMARY KEY AUTO_INCREMENT,
    customer_name VARCHAR(100) NOT NULL UNIQUE,  -- Assuming names are unique
    customer_city VARCHAR(50) NOT NULL
);

-- Table 2: Orders (references customers)
CREATE TABLE orders_3nf (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date DATE DEFAULT CURRENT_DATE,  -- Added for completeness
    FOREIGN KEY (customer_id) REFERENCES customers_3nf(customer_id)
);

-- Table 3: Products (unchanged from 2NF)
CREATE TABLE products_3nf (
    product_id INT PRIMARY KEY AUTO_INCREMENT,  -- Added surrogate key
    product_name VARCHAR(100) NOT NULL UNIQUE,
    product_price DECIMAL(10, 2) NOT NULL
);

-- Table 4: OrderItems (now with product_id instead of product_name)
CREATE TABLE order_items_3nf (
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL,
    unit_price DECIMAL(10, 2) NOT NULL,  -- Price at time of order
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id) REFERENCES orders_3nf(order_id),
    FOREIGN KEY (product_id) REFERENCES products_3nf(product_id)
);
