Step 2: Scenario 1 — FileSensor for Partner Data

Step 2a: Analyze the requirements
| Question | Answer |
|----------|--------|
| What are you waiting for? | A file to appear at path: `/data/partner/YYYY-MM-DD/transactions.csv` |
| Is the wait expected to be short (< 5 min) or long (potentially hours)? | Long (potentially hours) - file arrives anytime between midnight and 5 AM |
| What should happen if the condition is never met? | Pipeline should fail and alert the team |
| How frequently should we check? | Every 5 minutes (300 seconds) |


### Step 2b: Choose the sensor type

| Question | Answer |
|----------|--------|
| Selected Sensor Type | FileSensor |
| Reason for selection | We are waiting for a specific file to appear in the filesystem before processing can begin |

### Step 2c: Write the sensor configuration

# Scenario 1: Wait for Partner File Upload
wait_for_partner_file = FileSensor(
    task_id="wait_for_partner_file",
    filepath="/data/partner/{{ ds }}/transactions.csv",
    poke_interval=300,       # Check every 5 minutes
    timeout=7200,            # Fail after 2 hours (7200 seconds)
    mode="reschedule",       # Release worker slot between checks
    soft_fail=False,         # Hard fail — we need this file
    dag=dag,
)

# Downstream task — only runs after file is confirmed
process_partner_data = PythonOperator(
    task_id="process_partner_data",
    python_callable=process_transactions,
    dag=dag,
)

wait_for_partner_file >> process_partner_data



### Step 2d: Explain your parameter choices

| Parameter | Value | Justification |
|-----------|-------|---------------|
| filepath | /data/partner/{{ ds }}/transactions.csv | Uses Airflow template {{ ds }} to resolve to the execution date (e.g., 2026-02-19). This ensures each DAG run waits for the correct day's file |
| poke_interval | 300 (5 min) | The file arrives "sometime" in a multi-hour window. Checking every 5 minutes balances responsiveness against unnecessary I/O load on the file system |
| timeout | 7200 (2 hours) | Partner SLA is "before 5 AM". If the DAG starts at 3 AM and the file hasn't arrived by 5 AM, something is wrong. 2 hours gives enough buffer |
| mode | reschedule | The wait could last hours. In poke mode, the sensor would hold a worker slot doing nothing for up to 2 hours. reschedule releases the slot between checks, freeing compute for other tasks |
| soft_fail | False | This file is required. If it doesn't arrive, downstream tasks have no data to process. A hard failure triggers alerts so the team can investigate |

### Step 2e: Describe failure behavior

| Scenario | Behavior |
|----------|----------|
| File arrives late (but within 2 hours) | Sensor keeps checking every 5 min. Once file appears, sensor succeeds and downstream runs |
| File never arrives (timeout after 2 hours) | Sensor raises AirflowSensorTimeout. Task is marked FAILED. DAG run is marked FAILED. Alerts fire |
| File arrives but is empty (0 bytes) | FileSensor only checks file existence, not content. An additional validation task after the sensor should check file size and schema |
| File path is wrong (typo in date) | Sensor waits forever until timeout. Logs show the path it's checking — useful for debugging |

## Step 3: Scenario 2 — ExternalTaskSensor for Cross-DAG Dependency

### Step 3a: Analyze the requirements

| Question | Answer |
|----------|--------|
| What condition must be met before the ML pipeline starts? | The final_load task in the warehouse_refresh DAG must succeed |
| Do both DAGs run on the same schedule? | Yes, both are scheduled daily at midnight |
| What happens if warehouse_refresh fails — should the ML pipeline wait or skip? | The ML pipeline should fail - it cannot proceed without upstream data |

### Step 3b: Write the sensor configuration
# Scenario 2: Wait for Warehouse Refresh DAG to Complete
wait_for_warehouse = ExternalTaskSensor(
    task_id="wait_for_warehouse_refresh",
    external_dag_id="warehouse_refresh",
    external_task_id="final_load",
    execution_delta=timedelta(0),  # Same schedule — no delta needed
    poke_interval=120,             # Check every 2 minutes
    timeout=10800,                 # Fail after 3 hours
    mode="reschedule",
    soft_fail=False,
    dag=dag,
)

build_features = PythonOperator(
    task_id="build_ml_features",
    python_callable=build_feature_tables,
    dag=dag,
)

wait_for_warehouse >> build_features



### Step 3c: Explain your parameter choices

| Parameter | Value | Justification |
|-----------|-------|---------------|
| external_dag_id | warehouse_refresh | The specific DAG we depend on. Must match the DAG ID exactly |
| external_task_id | final_load | We wait for the last task in the DAG, not just any task. This ensures the entire refresh is complete |
| execution_delta | timedelta(0) | Both DAGs run at midnight daily. A delta of 0 means "wait for the same execution date" |
| poke_interval | 120 (2 min) | Warehouse refresh typically finishes by 2 AM. Checking every 2 minutes means we detect completion quickly |
| timeout | 10800 (3 hours) | If the warehouse hasn't finished in 3 hours (by 3 AM), something is likely broken upstream |
| mode | reschedule | Wait could be 1-2 hours. No need to hold a worker slot |
| soft_fail | False | ML pipeline cannot proceed without warehouse data - must fail if dependency fails |

### Step 3d: Describe failure behavior

| Scenario | Behavior |
|----------|----------|
| warehouse_refresh succeeds normally | ExternalTaskSensor detects success state and proceeds immediately to ML pipeline |
| warehouse_refresh fails | Sensor waits until timeout (3 hours) then fails. ML pipeline never runs |
| warehouse_refresh is delayed but eventually succeeds | Sensor continues checking every 2 minutes until success detected, then proceeds |
| execution_delta misconfigured | Sensor might wait for wrong execution date (e.g., yesterday's run). This could cause the sensor to wait forever or proceed at wrong time |

## Step 4: Scenario 3 — HttpSensor for API Health Check

### Step 4a: Analyze the requirements

| Question | Answer |
|----------|--------|
| What external condition must be true before pulling data? | API health endpoint must return HTTP 200 with {"status": "healthy"} |
| How often should we check? | Every 1 minute |
| What's the maximum time we should wait for the API? | 30 minutes |

### Step 4b: Write the sensor configuration
# Scenario 3: Wait for Vendor API to be Healthy
wait_for_api = HttpSensor(
    task_id="wait_for_vendor_api",
    http_conn_id="vendor_api",
    endpoint="/health",
    method="GET",
    response_check=lambda response: response.json().get("status") == "healthy",
    poke_interval=60,          # Check every 1 minute
    timeout=1800,              # Fail after 30 minutes
    mode="poke",               # Short expected wait — poke is fine
    soft_fail=False,
    dag=dag,
)

pull_catalog_data = PythonOperator(
    task_id="pull_catalog_data",
    python_callable=fetch_vendor_catalog,
    dag=dag,
)

wait_for_api >> pull_catalog_data



### Step 4c: Explain your parameter choices

| Parameter | Value | Justification |
|-----------|-------|---------------|
| http_conn_id | vendor_api | Connection ID stored in Airflow Connections. Contains the base URL https://api.vendor.com. Keeps credentials out of code |
| endpoint | /health | The lightweight health check endpoint. Does not consume API rate limits |
| method | GET | Health endpoints are standard GET requests |
| response_check | Lambda checking status == "healthy" | HTTP 200 alone is not sufficient — some APIs return 200 with {"status": "degraded"}. We check the response body |
| poke_interval | 60 (1 min) | API maintenance windows are usually short (15-30 min). Checking every minute means we resume quickly after maintenance ends |
| timeout | 1800 (30 min) | If the API is down for more than 30 minutes, it's likely a major outage — not a routine maintenance window. Fail and alert |
| mode | poke | Expected wait is short (0-15 minutes during maintenance). The overhead of rescheduling is not worth it for short waits |

### Step 4d: Describe failure behavior

| Scenario | Behavior |
|----------|----------|
| API returns 200 immediately | Sensor succeeds instantly, no wait needed, proceeds to data pull |
| API returns 503 for 10 minutes then recovers | Sensor continues checking every minute until health check passes at 10 minutes, then proceeds |
| API is down for over 30 minutes | Sensor times out after 1800 seconds, task fails, DAG fails, alerts triggered |
| API returns 200 but body says {"status": "degraded"} | Response check fails, sensor continues waiting until timeout |
| Network error (connection refused) | HttpSensor treats connection errors as failures. The sensor will fail if it can't reach the endpoint |

## Step 5: Scenario 4 — TimeSensor for Business Time Gate

### Step 5a: Analyze the requirements

| Question | Answer |
|----------|--------|
| What condition must be met? | Current time must be 6:00 AM or later |
| Is this a hard business rule or a soft preference? | Hard business rule - reports cannot be generated before 6 AM |
| What timezone should the sensor use? | Should match business timezone (assume local timezone, not UTC) |

### Step 5b: Write the sensor configuration
# Scenario 4: Wait Until 6:00 AM Before Generating Reports
from datetime import time as dt_time

wait_for_business_hours = TimeSensor(
    task_id="wait_for_6am",
    target_time=dt_time(6, 0, 0),    # 6:00:00 AM
    poke_interval=60,                  # Check every minute
    mode="reschedule",                 # Could wait hours — release slot
    timeout=14400,                     # 4-hour safety timeout
    dag=dag,
)

generate_revenue_report = PythonOperator(
    task_id="generate_revenue_report",
    python_callable=build_revenue_report,
    dag=dag,
)

wait_for_business_hours >> generate_revenue_report




### Step 5c: Explain your parameter choices

| Parameter | Value | Justification |
|-----------|-------|---------------|
| target_time | time(6, 0, 0) | Business rule: no reports before 6 AM. This is the earliest allowed time |
| poke_interval | 60 (1 min) | We want reports to start promptly at 6 AM, not 6:05 AM. Checking every minute ensures we start within 1 minute of the target |
| mode | reschedule | If upstream finishes at 4 AM, the sensor waits 2 hours. Reschedule mode avoids holding a worker slot for 2 hours |
| timeout | 14400 (4 hours) | Safety net. If the DAG somehow starts at 11 PM, the sensor waits up to 4 hours. If it hasn't hit 6 AM by then, something is misconfigured |

### Step 5d: Describe failure behavior

| Scenario | Behavior |
|----------|----------|
| DAG starts at 5 AM | Sensor waits 1 hour, checking every minute, succeeds at 6 AM exactly, proceeds to report generation |
| DAG starts at 7 AM | Sensor succeeds immediately (time already past 6 AM), no wait |
| Timezone mismatch | Critical failure: If DAG uses UTC but business rule is in EST, reports would generate 5 hours early (11 PM previous day instead of 6 AM) |
| DAG starts extremely early (11 PM previous day) | Sensor waits up to 4 hours, then times out if 6 AM hasn't been reached yet |

## Step 6: Sensor Comparison Summary

| # | Scenario | Sensor Type | poke_interval | timeout | mode | soft_fail | Key Risk |
|---|----------|-------------|---------------|---------|------|-----------|----------|
| 1 | Partner file upload | FileSensor | 300s (5 min) | 7200s (2 hr) | reschedule | False | File never arrives |
| 2 | Cross-DAG dependency | ExternalTaskSensor | 120s (2 min) | 10800s (3 hr) | reschedule | False | Upstream DAG fails |
| 3 | API health check | HttpSensor | 60s (1 min) | 1800s (30 min) | poke | False | Extended API outage |
| 4 | Business time gate | TimeSensor | 60s (1 min) | 14400s (4 hr) | reschedule | False | Timezone mismatch |

### General Approach to Choosing poke vs reschedule Mode

| Mode | Best For | Reasoning |
|------|----------|-----------|
| poke | Short expected waits (< 5-10 minutes) | The overhead of rescheduling would be greater than simply holding the worker slot. Keeps sensor active in memory for brief checks |
| reschedule | Long expected waits (potentially hours) | Releases worker slot between checks, freeing compute for other tasks. Ideal for overnight file uploads or business time gates |
