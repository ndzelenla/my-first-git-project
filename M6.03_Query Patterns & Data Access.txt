WITH customer_transactions AS (
    SELECT 
        customer_id,
        order_date,
        total_amount,
        -- Running totals
        SUM(total_amount) OVER (
            PARTITION BY customer_id 
            ORDER BY order_date 
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS running_total,
        -- Moving averages (30-day, 90-day)
        AVG(total_amount) OVER (
            PARTITION BY customer_id 
            ORDER BY order_date 
            RANGE BETWEEN INTERVAL '30 days' PRECEDING AND CURRENT ROW
        ) AS avg_30day,
        -- Percent of total per customer
        total_amount * 100.0 / SUM(total_amount) OVER (
            PARTITION BY customer_id
        ) AS pct_of_customer_total,
        -- Sequence patterns (days between orders)
        LAG(order_date) OVER (
            PARTITION BY customer_id 
            ORDER BY order_date
        ) AS previous_order_date,
        EXTRACT(DAY FROM order_date - LAG(order_date) OVER (
            PARTITION BY customer_id 
            ORDER BY order_date
        )) AS days_since_last_order,
        -- Order rank within customer
        ROW_NUMBER() OVER (
            PARTITION BY customer_id 
            ORDER BY order_date
        ) AS order_sequence,
        -- Monetary decile across all customers
        NTILE(10) OVER (
            ORDER BY total_amount DESC
        ) AS amount_decile
    FROM orders
    WHERE order_date >= '2023-01-01'
)
SELECT 
    customer_id,
    order_date,
    total_amount,
    running_total,
    avg_30day,
    ROUND(pct_of_customer_total, 2) AS pct_of_customer_total,
    days_since_last_order,
    order_sequence,
    amount_decile,
    -- Customer lifecycle stage based on sequence
    CASE 
        WHEN order_sequence = 1 THEN 'First-time Buyer'
        WHEN order_sequence BETWEEN 2 AND 5 THEN 'Early-stage'
        WHEN order_sequence BETWEEN 6 AND 20 THEN 'Growth-stage'
        WHEN order_sequence > 20 THEN 'Mature'
    END AS customer_lifecycle_stage,
    -- Purchase frequency category
    CASE 
        WHEN days_since_last_order IS NULL THEN 'New'
        WHEN days_since_last_order <= 7 THEN 'Hyper-active'
        WHEN days_since_last_order <= 30 THEN 'Active'
        WHEN days_since_last_order <= 90 THEN 'Dormant'
        ELSE 'At-risk'
    END AS engagement_level
FROM customer_transactions
ORDER BY customer_id, order_date;

## Document stores

- What they are - they are Nosql databases that store data as flexible, self describing documents (typically in json, sml or yaml)
- Key characteristics - Schema flexibility, self contained, horizontal scalability and replication
- Use cases - Content Management Systems, real time applications and IOT applications
- Examples (MongoDB, CouchDB)

## Key-Value stores

- What they are - they are Nosql databases that store data as siimple key value pairs, where the key is a unique identifier and the value is the data itself
- Key characteristics - extremely simple (get/set/put/delete), fast oerformance, not just in memory and scaling is horizontal
- Use cases - accelerating applications, stateless applications and real time features
- Examples (Redis, DynamoDB)

## Wide-column databases

- What they are - a NoSQL database that stores data in tables, rows, and dynamic columns, but organizes data by column families rather than by row. 
-It is designed to handle massive amounts of data across distributed systems, offering high performance and scalability for both reads and writes.
- Key characteristics - Column family storage, dynamic schema,horizontal scalability, high write throughput, compression friendly, No joins
- Use cases - Time series data, content management, event logging
- Examples (Cassandra, HBase)

# Graph databases

- What they are - A graph database is a type of NoSQL database that uses graph structures to represent and store data. Instead of tables or documents, 
- it models data as nodes (entities), relationships (connections between entities), and properties (attributes) 
- Key characteristics - schema optional, ACID compliance, real time relationship queries
- Use cases - social network, fraud detection, knowledge graphs, recommendation engines
- Examples (Neo4j, Amazon Neptune, Arango DB)

## ACID properties with examples

- Atomicity: What it means, provide an example -ensures a transaction is treated as a single, indivisible piece of work. Either all operations complete successfully or none do. e.g bank transfer
- Consistency: What it means, provide an example -ensures that a transaction brings the database from one valid state to another valid state, maintaining all predifined rules and constraints. e.g inventory management
- Isolation: What it means, provide an example -ensures that concurrent transactions execute indipendently without interfering with each other.e.g concurrent bank transfers
- Durability: What it means, provide an example -ensures that once a transaction is committed, its changes are permanent and will persist any subsequent system failure . e.g order confirmation
- When ACID is critical - in financial systems, healthcare systems, government and legal

##BASE properties with examples

- Basically Available: What it means, provide an example - BASE is an alternative database design philosophy that prioritizes availability and scalability over immediate consistency. e.g social media platform
- Soft state: What it means, provide an example - The state of the system may change over time without any input, due to eventual consistency and background replication processes. e.g shopping card
- Eventual consistency: What it means, provide an example - Given enough time without new updates, all replicas will eventually converge to the same state e.g youtube like counts
- When BASE is acceptable - social media and content platforms, content delivery and caching, analytics and monitoring

## Why BASE is acceptable in some systems

- Explain scenarios where eventual consistency is fine - social media interations because users don't need to see the exact counts immediately and even when the counts are off temporaly by 1 or 2, there is no real harm
- Discuss trade-offs between ACID and BASE -

## **1. Consistency**

| Aspect | RDBMS | NoSQL | Trade-offs |
|--------|-------|-------|------------|
| **Approach** | Strong, immediate consistency (ACID) | Varies: eventual to strong consistency | **RDBMS**: Guaranteed correctness but potential performance hit<br>**NoSQL**: Performance/scalability vs. consistency |
| **Transaction Model** | ACID-compliant with multi-statement transactions | Often BASE; limited or no multi-document/row transactions | **RDBMS**: Complex operations remain atomic<br>**NoSQL**: Application must handle partial failures |
| **Read Behavior** | Always returns the most recent committed data | May return stale data (eventual consistency) | **RDBMS**: Predictable but slower<br>**NoSQL**: Faster reads but may be outdated |
| **Write Behavior** | Synchronous replication | Often asynchronous replication | **RDBMS**: Data safe but higher latency<br>**NoSQL**: Lower latency but risk of data loss on failure |
| **Conflict Resolution** | Prevented via locks | Application-defined (last-write-wins, vector clocks, CRDTs) | **RDBMS**: Automatic but blocking<br>**NoSQL**: Flexible but complex to implement |
| **Examples** | COMMIT ensures all-or-nothing | Cassandra (tunable), MongoDB (eventual), DynamoDB (configurable) | |

---

## **2. Scalability**

| Aspect | RDBMS | NoSQL | Trade-offs |
|--------|-------|-------|------------|
| **Primary Scaling** | Vertical scaling (scale-up) | Horizontal scaling (scale-out) | **RDBMS**: Hardware limits, expensive<br>**NoSQL**: More cost-effective, no single point of failure |
| **Architecture** | Monolithic, single-server or master-slave replication | Distributed, shared-nothing architecture | **RDBMS**: Simpler to manage<br>**NoSQL**: More complex coordination |
| **Partition Tolerance** | Poor (CAP theorem: CP systems) | Excellent (CAP theorem: AP or CP options) | **RDBMS**: May become unavailable during partitions<br>**NoSQL**: Remains available but may sacrifice consistency |
| **Data Distribution** | Manual sharding (complex) | Automatic sharding (built-in) | **RDBMS**: Manual effort, expertise required<br>**NoSQL**: Simpler scaling, but may affect query patterns |
| **Max Practical Scale** | TBs to few PBs with specialized hardware | 100s of PBs across 1000s of nodes | **RDBMS**: Limits reached sooner<br>**NoSQL**: Almost limitless horizontal growth |
| **Performance at Scale** | Degrades with joins/complex queries | Maintains performance for simple operations | **RDBMS**: Query optimization harder at scale<br>**NoSQL**: Predictable performance for specific patterns |

---

## **3. Query Flexibility**

| Aspect | RDBMS | NoSQL | Trade-offs |
|--------|-------|-------|------------|
| **Query Language** | SQL (standardized, declarative) | Varies: proprietary, limited, or SQL-like | **RDBMS**: Portable skills, powerful expressions<br>**NoSQL**: Learning curve, vendor lock-in |
| **Join Operations** | Native, multi-table joins | Generally no joins; denormalized data | **RDBMS**: Flexible relationships<br>**NoSQL**: Application-side joins or data duplication |
| **Aggregation** | Rich: GROUP BY, window functions, subqueries | Limited or specialized (MapReduce, aggregation pipelines) | **RDBMS**: Complex analytics out-of-box<br>**NoSQL**: May require external processing |
| **Ad-hoc Queries** | Excellent (any column, any condition) | Limited (often need predefined indexes) | **RDBMS**: Exploratory analysis friendly<br>**NoSQL**: Requires upfront query pattern knowledge |
| **Indexing** | Multiple index types (B-tree, hash, etc.) | Usually simpler indexing (often primary only) | **RDBMS**: Flexible optimization<br>**NoSQL**: Simpler but less query flexibility |
| **Examples** | `SELECT * FROM users JOIN orders ON...` | MongoDB: `db.collection.find({age: {$gt: 25}})`<br>Cassandra: Limited WHERE clause options | |

---

## **4. Schema Rigidity**

| Aspect | RDBMS | NoSQL | Trade-offs |
|--------|-------|-------|------------|
| **Schema Definition** | Schema-on-write (rigid, predefined) | Schema-on-read (flexible, dynamic) | **RDBMS**: Data quality enforced<br>**NoSQL**: Rapid iteration possible |
| **Schema Changes** | ALTER TABLE (can be expensive, blocking) | Dynamic, no migration needed | **RDBMS**: Safe but slow evolution<br>**NoSQL**: Fast changes but potential data inconsistencies |
| **Data Types** | Strict, predefined types | Flexible, often JSON/BSON documents | **RDBMS**: Type safety, validation<br>**NoSQL**: Schema-less, heterogeneous data |
| **Null Values** | Explicitly defined columns, NULLs allowed | No storage for missing fields | **RDBMS**: Predictable structure<br>**NoSQL**: Sparse data efficient |
| **Data Integrity** | Enforced (PK, FK, constraints, triggers) | Application responsibility | **RDBMS**: Automatic integrity<br>**NoSQL**: Developer must ensure consistency |
| **Evolution Example** | Adding a column: `ALTER TABLE users ADD COLUMN...` | Just start writing new fields to documents | **RDBMS**: All rows updated (potentially slow)<br>**NoSQL**: Only new documents have field |

## Step 4
# Banking system

- Recommended storage type - RDBMS 
- Justification based on: 
- Data structure requirements - Highly structured: accounts, customers, transactions, balances. Strong relationships (customers have accounts, accounts have transactions) with referential integrity needs
- Consistency Needs - ACID mandatory: Transactions must be atomic (transfers all-or-nothing), consistent (balances always correct), isolated (concurrent transfers don't interfere), durable (once committed, permanent)
- Query Patterns - Complex joins: "Show all transactions for customer X between dates Y-Z with vendor W". Aggregations: "Daily balance summaries", "Monthly interest calculations".
- Scalability requirements - Moderate-high scale but not "internet-scale". Vertical scaling often sufficient. Predictable growth.

# E-commerce platform

- Recommended storage type - RDBMS for transactional data
-Justification based on:
- Data structure requirements - Mixed: Structured (orders, payments, inventory), semi-structured (product catalogs with varying attributes), unstructured (reviews, images).
- Consistency Needs - • ACID needed for: Inventory (last item), payments, orders
• Eventual consistency acceptable for: Product recommendations, reviews, user wishlists
• Session data: Can be eventually consistent
- Query Patterns - • Complex joins for order history, reporting
• Simple key-value for sessions
• Full-text search for product discovery
• Aggregations for analytics
- Scalability requirements - High and variable: Black Friday spikes, global expansion. Need horizontal scaling for user-facing components.

# Telecom call data records (CDR)

- Recommended storage type - Apache Cassandra, HBase,
- Justification based on:
- Data structure requirements - Semi-structured but consistent format: call timestamps, source/destination numbers, duration, cost. High volume with predictable columns.
- Consistency Needs - Eventual consistency acceptable: Billing can be slightly delayed. Call records are write-once, read-many. No updates after creation.
- Query Patterns - • Primary: High-volume writes (millions of calls/day)
• Read patterns: Time-range queries ("all calls from 2-3pm"), aggregation by customer/region
• Minimal joins: Each CDR is mostly independent
- Scalability requirements - Extremely high: Millions of customers, billions of calls monthly. Must scale horizontally across data centers. High write throughput critical.

# Logging systems

- What is the primary operation? - WRITE operations - Appending log entries (application logs, system metrics, audit trails, error logs)
- Is it read-heavy or write-heavy? - write heavy
- Explain why - High volume of writes: Every application action, user request, system event generates log entries, Continuous streaming: Logs are generated 24/7, often with high velocity (thousands to millions of events per second)
- What are the implications for storage design? - Optimize for append-only operations, sequential writes, minimal indexing, Horizontal scaling to handle load Spikes, Ensure no log loss even during failures

- Reporting Dashboards - 
- What is the primary operation? - READ operations - Aggregating, filtering, and visualizing data
- Is it read-heavy or write-heavy? - read heavy
- Explain why - Continuous queries: Dashboards refresh automatically (every 30s, 1min, 5min),Multiple concurrent users: Many stakeholders viewing dashboards simultaneously,Read ratio: Often 1000:1 or higher read-to-write ratio
- What are the implications for storage design? - fast aggregations(Pre-compute aggregates, materialized views, Caching),Support many simultaneous queries without locking,Heavy caching of dashboard results

- Transactional APIs

- What is the primary operation? - Mixed but balanced - Both reads and writes with transactional integrity
- Is it read-heavy or write-heavy? - both
- Explain why - CRUD operations: Create, Read, Update, Delete all occur regularly,User interactions: Every action involves read (check state) → process → write (update state)
- What are the implications for storage design? - ACID compliance, low latency, concurrent Access

What are aggregation queries? - Aggregation queries compute summary statistics across multiple records using operations like: Count(),sum(),avg(),min(),max()
When do they dominate? - Business intelligence & analytics dashboards, Financial reporting (daily sales, quarterly revenue),Monitoring systems (average response times, error rates)

What is document embedding? - Document embedding involves nesting related data within a single document/record rather than storing it in separate tables and joining.
When is it preferable? - Bounded one-to-many relationships: User with orders, blog post with comments, Data accessed together: If you always fetch user with their last 5 orders, Hierarchical data: Categories with subcategories with products
What storage systems support embedding? - MongoDB, Couchbase

Impact on performance and maintenance 

How does aggregation affect performance? - Columnar storage: Process columns independently, better compression, Parallel processing: Distribute aggregation across multiple nodes
How does embedding affect performance? - Single read operation: Fetch all related data in one go, No joins: Eliminates join computation Overhead, Predictable performance: Document size known in advance
What are the maintenance trade-offs? - data Consistency, backup, data Quality, Schema changes
When to choose each Approach - Analytical Workloads → Columnar database like Redshift/BigQuery, Time-Series Analysis → Time-series database like TimescaleDB,  Large-Scale Reporting → OLAP system like Druid,
Content Management Systems → MongoDB, fetch entire post in one query, User Profiles with Preferences → Couchbase, single document per user

## Summarize how query patterns influence:

Schema design

How do read patterns influence schema? - Key Principle: Denormalize for reads, normalize for writes

What factors matter most? - Read/Write Ratio, Data Access Pattern, Query Complexity

Indexing strategy

How do query patterns influence indexing? - Index Selection Based on Query Patterns: Equality searches -> B-tree/Hash Indexes, Text search -> Full-text indexes
What indexes support read-heavy workloads? - Strategy: "Index everything you query, nothing you don't", Covering indexes: Include all queried columns, Composite indexes: Order by selectivity (most selective first)
What indexes support write-heavy workloads? - Strategy: "Minimize indexes, batch updates, optimize structure", Fewer indexes: Each index adds write Overhead, Append-only designs: No updates to indexed columns
